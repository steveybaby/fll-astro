# Signups Backend — Design

**Date:** 2026-08-17
**Status:** Approved for planning
**Scope:** Replaces the Google Apps Script signup backend with a Cloudflare Worker
backed by D1. This is the "spec 2" deliberately deferred by the BIOGLOW Season Reset
spec, which built `src/lib/signups.ts` as the seam this migration would use.

---

## Problem

RSVPs and snack duty are stored in a Google Sheet and reached through an Apps Script
web app. Three things are wrong with it, measured rather than assumed.

### It is slow

A single call takes **~2.25 seconds**, consistently, measured three times against the
live endpoint. Every meeting page makes **two** of them — one for RSVPs, one for snacks —
so roughly **4.5 seconds** pass before a parent can see or change anything.

The payload is **13 KB**. This is not a data-volume problem; it is Apps Script overhead.
The same bytes from an edge worker should land in tens of milliseconds.

### It fetches everything, every time

Neither endpoint accepts a working date filter in practice: the client requests the
entire dataset — all 32 meetings × 12 people — and filters in JavaScript. A meeting page
needs one row and downloads all of them, twice.

### It cannot be used for most of this season — a deadlock

This is the serious one, and it is a genuine functional break, not a slowness complaint.

The Apps Script `update` handler creates a sheet row on demand (`appendRow` when the
date is not found). So a row exists only *after* somebody has RSVP'd.

`RSVPComponent.astro` does this when the row is missing:

```js
if (meetingData) {
  this.renderRSVPData(meetingData.kids);
  this.showContent();                                  // controls rendered
} else {
  this.showError(`No RSVP data found for meeting date: ${this.meetingDate}`);
}                                                      // controls never rendered
```

The controls are never shown, so nobody can create the first RSVP, so the row is never
created. Verified live in production:

| Meeting | Sheet row | Error shown | Controls visible |
|---|---|---|---|
| `2026-08-23` | yes | no | **yes** |
| `2026-09-13` | no | yes | **no** |

The backend holds only **3** of this season's 21 meetings (`2026-08-16`, `2026-08-23`,
`2026-11-15`). **Nobody can RSVP to the other 18.** The UI presents this as an error with
a "Try Again" button that cannot ever help.

### Secondary: the two endpoints disagree about dates

`get` returns `"2026-08-16"`. `getSnacks` returns `"2026-08-16T07:00:00.000Z"`. Each
component carries its own normalisation code to cope. The two sheets have also drifted —
snacks has a `2026-09-06` row that RSVPs does not.

## Goals

1. Signups work for every meeting, including ones nobody has touched.
2. Interactions feel immediate — target **under 200 ms**, against 2,250 ms today.
3. One date format, one source of truth for the roster.
4. No page or component needs to know the backend changed, beyond the deadlock fix.

## Non-goals

- Authentication. The endpoint stays open, as it is today (see Access below).
- Changing what RSVP statuses mean, or the snack-duty rules.
- Touching the 2025-26 archive, which reads frozen JSON and never calls the API.
- Redesigning the signup UI.

---

## Access

The current endpoint is public: its URL is in the page source, so anyone can set any
child's RSVP. This is unchanged by design — nine families, low-stakes data, no history of
abuse, and per-family accounts would be disproportionate.

"Open" is not the same as "unvalidated". The Worker rejects writes whose person is not on
the current roster, or whose date is not a real meeting in the current season. That
prevents an open endpoint from accumulating junk rows and misspelled names, which is what
actually degrades a system like this.

---

## Architecture

### Components

| Component | Responsibility |
|---|---|
| `workers/signups/` | Cloudflare Worker: the HTTP API and all validation |
| D1 database `fll-signups` | One table, `signups` |
| `/signups-config.json` | Generated by the site at build: the roster and valid meeting dates |
| `src/lib/signups.ts` | Unchanged public surface; internals repointed at the Worker |

The site itself remains a fully static GitHub Pages deployment. The Worker is a separate
deployable with its own `wrangler.toml`, and is the only new running component.

### API

Meeting-scoped, so a page fetches one meeting rather than the season.

```
GET    /signups?date=YYYY-MM-DD
       → 200 { meetingDate, rsvps: [{ name, status }], snack: string | null }

POST   /rsvp    { date, name, status }        → 200 { ok: true }
POST   /snack   { date, name }                → 200 { ok: true }
DELETE /snack?date=YYYY-MM-DD&name=Ishaan     → 200 { ok: true }
```

`DELETE` takes query parameters rather than a body: bodies on DELETE are inconsistently
supported across fetch implementations and proxies, and there is nothing here that needs
one.

All dates are `YYYY-MM-DD`, everywhere, with no timestamps. The Worker rejects anything
else with 400 rather than coercing it — silent coercion is what produced the current
mismatch.

**`GET` always returns the complete roster**, with `status: ""` for anyone who has not
answered. This is the contract change that makes the deadlock structurally impossible:
there is always something to render, so the component never has an empty branch to fail
into. A meeting nobody has touched returns the same shape as a fully answered one.

### Storage

```sql
CREATE TABLE signups (
  meeting_date TEXT NOT NULL,           -- YYYY-MM-DD
  person       TEXT NOT NULL,           -- must match a roster name
  kind         TEXT NOT NULL,           -- 'rsvp' | 'snack'
  value        TEXT NOT NULL,           -- status string, or '1' for snack duty
  updated_at   TEXT NOT NULL,           -- ISO 8601
  PRIMARY KEY (meeting_date, person, kind)
);
```

Writes are upserts on the primary key. Snack duty is one person per meeting: `POST /snack`
deletes existing `kind='snack'` rows for that date and inserts the new one in a single
transaction, so there is never a window with two assignees.

Storing both kinds in one table keeps the read path to a single query per meeting. The
alternative — separate tables — would need two queries or a join for no benefit at this
size.

### Roster and date validation

The Worker must know which names and dates are legitimate. It must not hold its own copy:
`src/config/season.ts` is the single source of truth for the roster, and a second copy
inside the Worker would drift the first time the roster changes and nobody remembers.

The site therefore generates, at build time, a static endpoint from `season.ts` and the
meetings content collection:

```jsonc
// /signups-config.json
{
  "season": "2026-27",
  "people": ["Jasper", "Ethan", "Luca", "Ishaan", "Hudson", "Eli", "Steve H", "Steve S", "Aditi"],
  "meetingDates": ["2026-08-16", "2026-08-23", "..."]
}
```

The Worker fetches this and caches it in memory for five minutes. A cold cache costs one
extra hop; in exchange the roster can never be wrong in one place and right in another.

**Rejected alternative:** hardcoding the roster in the Worker's environment variables.
Fewer moving parts, but it silently drifts at every season reset — exactly the class of
bug the season-reset spec was written to eliminate.

**Failure mode:** if the config fetch fails and no cached copy exists, the Worker serves
reads normally and rejects **writes** with 503. Reads carry no risk from a stale roster;
writes are what need validating.

### Client

`src/lib/signups.ts` keeps all five exported functions with their current signatures:
`getRSVPs`, `updateRSVP`, `getSnacks`, `assignSnack`, `removeSnack`. Only the internals
change. Its five consumers — `RSVPComponent.astro`, `SnackDutyComponent.astro`,
`rsvps.astro`, `coach_rsvps.astro`, `snacks.astro` — need no changes for the backend swap.

**One in-flight request per meeting.** `GET /signups` returns RSVPs and snack duty
together, but the client exposes them as two functions, and a meeting page calls both.
Naively that is two identical round trips — which would undercut the whole point of
collapsing the read path.

`signups.ts` therefore keeps a short-lived promise cache keyed by date: whichever of
`getRSVPs` or `getSnacks` is called first starts the fetch, the second awaits the same
promise, and each maps the shared response into the shape its caller expects. The cache
entry is dropped once resolved, plus after any write to that date, so a write is always
followed by fresh data.

Three client changes are in scope:

1. **The deadlock branch** in `RSVPComponent.astro` is fixed rather than left unreachable.
   The new contract means it should never trigger, but a component that strands its own UI
   when a fetch returns something unexpected is a bug regardless of whether the current
   backend can produce that state.
2. **Date-normalisation code** in the components becomes dead once the API is strict about
   `YYYY-MM-DD`, and is removed.
3. **The promise cache** described above, so the combined endpoint is fetched once per
   meeting rather than once per function.

## Data flow

**Read.** Meeting page → `getRSVPs(date)` → `GET /signups?date=…` → one D1 query →
roster merged with stored values → JSON. One round trip, a few hundred bytes.

**Write.** Button press → optimistic UI update (already implemented) →
`updateRSVP(date, name, status)` → `POST /rsvp` → validate against cached config →
upsert → `{ ok: true }`. On failure the existing cache-and-toast path applies.

## Error handling

| Condition | Behaviour |
|---|---|
| Meeting has no stored signups | 200 with the full roster, all statuses `""` |
| Date not in the current season | 400 `{ error: "unknown meeting date" }` |
| Person not on the roster | 400 `{ error: "unknown person" }` |
| Malformed date | 400; never coerced |
| Config unavailable, no cache | Reads succeed; writes 503 |
| D1 error | 500; client keeps its cached view and shows the existing toast |
| Worker unreachable | Client keeps its cached view and shows the existing toast |

## Migration

Small enough to state exactly. The 2025-26 history is already frozen in
`src/data/2025-26-history.json` and read only by `ArchivedSignups.astro`, so nothing
historical needs moving.

Current-season data in the Sheet, in full:

| Date | RSVPs | Snack |
|---|---|---|
| `2026-08-16` | 7 (Jasper, Eli, Ishaan, Hudson, Luca, Ethan, Steve H — all 👍) | Jasper |
| `2026-08-23` | 2 (Jasper 👍, Steve H 👎) | — |
| `2026-11-15` | 0 (empty row) | — |
| `2026-09-06` | — | 0 (empty row, snacks sheet only) |

**Ten values.** A one-off script reads both Apps Script endpoints and writes to D1, so the
migration is reproducible and verifiable rather than retyped.

**The roster shrinks from 12 columns to 9 people.** The Sheet still carries Asher, Kai and
Jeremiah from the 2025-26 team. None of them appears in any current-season row, so nothing
is lost — but the migration script must treat an unknown name as an error to investigate
rather than silently skipping it, since silently skipping is how a real signup would go
missing unnoticed.

## Cutover and rollback

`SIGNUP_API_URL` in `src/lib/signups.ts` is the only switch. The Apps Script deployment
and its Sheet stay untouched and unused for at least one full meeting cycle, so rollback
is reverting one commit — no data recovery needed, because the Sheet still holds
everything it held before.

## Deployment

The Worker deploys with `wrangler deploy`, run manually to begin with. Automating it in
CI needs a Cloudflare API token as a repository secret, which is worth doing later but
widens the scope of this change for no functional gain — the Worker will change far less
often than the site.

## Testing

**Baselines to hold:** `npm test` is at 78 passing, `npm run build` exits 0, and
`npm run check` reports 62 errors / 0 warnings. None may regress.

**Worker tests** — handler-level, against a real D1 binding in `wrangler dev`:

| Test | Assertion |
|---|---|
| Untouched meeting | Returns full roster, every status `""` |
| Partly answered meeting | Stored values present, unanswered blank |
| RSVP upsert | Second write for the same person replaces, not duplicates |
| Snack exclusivity | Assigning a second person leaves exactly one assignee |
| Unknown person | 400, nothing written |
| Unknown date | 400, nothing written |
| Timestamp date format | 400, not coerced |
| Config unavailable | Reads succeed, writes 503 |

**Client tests** — `signups.ts` against a mocked fetch, asserting each of the five
operations produces the documented request and parses the documented response, plus:
calling `getRSVPs` and `getSnacks` for the same date issues **one** fetch, and a write to
that date invalidates the cache so the next read goes to the network.

**Manual, and the one that matters most:** open a meeting page for a date with no stored
data — `2026-09-13` — and complete an RSVP. This is the exact flow that is impossible
today, and it must work before cutover.

**Performance check:** the `GET` path measured under 200 ms, against the 2,250 ms
baseline recorded in this spec.

## Risks

**A new always-on dependency.** Today an Apps Script outage breaks signups; afterwards a
Worker or D1 outage does. Net reliability should improve, but the failure mode is new and
the client's cache-and-toast path is what covers it.

**Cloudflare account coupling.** Photos already depend on R2 in the same account, so a
billing or account problem would now take out signups as well as images. Acceptable for a
hobby site, worth stating.

**An open write endpoint remains open.** Validation stops malformed and unknown-name
writes, but anyone who finds the URL can still set a real child's real RSVP. This is a
deliberate, unchanged trade-off, not an oversight.
